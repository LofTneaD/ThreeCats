## Выбор режима рендеринга Blazor

Для проекта выбран режим **Interactive Server** в приложении Blazor Web App.

В этом режиме интерактивная логика компонентов выполняется на сервере, а взаимодействие с браузером организуется через SignalR. Это позволяет не загружать в браузер сборки .NET и основную серверную логику приложения.

Режим подходит для разрабатываемой системы ветеринарной клиники, поскольку бизнес-логика, работа с базой данных и обработка запросов будут выполняться на сервере.

**Почему не WebAssembly?**

Blazor WebAssembly выполняет .NET-код непосредственно в браузере. Такой вариант увеличивает объём кода, загружаемого клиентом, и требует особого внимания к разграничению клиентской и серверной логики. Для проекта, ориентированного на серверную работу с PostgreSQL и авторизацией, этот режим не является приоритетным.

**Почему не Auto?**

Режим Auto может использовать серверную интерактивность и WebAssembly в зависимости от доступности клиентской среды и загрузки необходимых ресурсов. Он усложняет первоначальную настройку и тестирование, а его преимущества не являются необходимыми для текущих требований проекта.

## Модель ветвления

В проекте используется упрощённая модель GitHub Flow.

main — основная ветка со стабильной версией проекта.

feature/<name> — разработка новой функциональности.

fix/<name> — исправление ошибок.

docs/<name> — изменение документации.

test/<name> — добавление и изменение тестов.

Формат сообщений коммитов:

feat — новая функциональность;

fix — исправление ошибки;

docs — документация;

test — тесты;

refactor — переработка кода без изменения поведения;

## Архитектура проекта

Проект организован по логическим слоям в рамках одного ASP.NET Core проекта.

Components — пользовательский интерфейс на Blazor.

Application — прикладные сервисы, интерфейсы и сценарии работы приложения.

Domain — сущности и бизнес-правила предметной области.

Data — доступ к данным, контекст Entity Framework Core, конфигурации сущностей и миграции.

Configuration — типизированные настройки приложения.

## Правила зависимостей

UI обращается к прикладной логике через интерфейсы сервисов Application.

Application зависит от Domain, но не от конкретной реализации хранения данных.

Data реализует интерфейсы доступа к данным, определённые на уровне Application, и работает с сущностями Domain.

Domain не зависит от UI, базы данных и инфраструктуры.

Регистрация прикладных сервисов выполняется централизованно через метод AddApplicationServices().
